# 软件著作权登记申请（软著）

> 范围：本 skill 覆盖中国版权保护中心 R11 软件著作权登记申请（线上填报）的字段要求、材料规范与项目分析方法。原始抓取数据在 `docs/pages/raw/`，逐字段细节见 `references/` 下三页字段文档。

## 1. 申请流程概览

线上办理（https://register.ccopyright.com.cn/r11.html），免费，6 步：

1. 选择办理身份 → 2. 软件申请信息 → 3. 软件开发信息 → 4. 软件功能与特点 → 5. 确认信息 → 6. 填报完成

agent 能辅助的是第 2、3、4 步的字段填报和鉴别材料生成；第 1 步（办理身份/实名认证）和第 5 步（确认签章）必须由用户完成。

## 2. 硬性规范速查（写整改建议时引用）

### 2.1 鉴别材料（第 4 页上传，官方原文要求）

- **源程序**：连续的前 30 页 + 连续的后 30 页（可按开发时间排序，也可按功能主次自定义排序），**每页不少于 50 行**。整体不到 60 页（约 3000 行）则提交全部。PDF 格式。
- **文档**（程序设计说明书/流程图/用户手册等任一）：前 30 页 + 后 30 页，**每页不少于 30 行**。不到 60 页提交全部。PDF 格式。可上传多份。
- **一致性**：程序和文档中出现的权利人署名、软件名称及版本号，必须与申请表其他内容一致。
- **例外交存**：一般交存之外的替代方式，选后需选具体方式（细节待补充抓取）。

### 2.2 命名与版本号

- 软件全称：简短明确、针对性强，**所有申请材料中保持一致**；惯例为"品牌 + 用途功能 +（系统/平台/软件）"
- 简称：没有就留空，**不要填"无"**
- 版本号：`V数字` 或 `数字` 格式，如 V1.0、2.0.1

### 2.3 日期逻辑

- 开发完成日期 = 软件全部固定在有形物体上的日期，不得晚于申请日
- 已发表时：首次发表日期不得早于开发完成日期；需填发表地点（国家+省市）

### 2.4 开发方式与权属文件（整改提醒的关键触发点）

| 开发方式 | 需额外提交的权属证明 |
|---|---|
| 单独开发 | 无 |
| 合作开发 | 合作开发合同或协议（书面） |
| 委托开发 | 委托开发合同或协议（书面） |
| 下达任务开发 | 项目任务书或合同（书面） |

非单独开发时还需确认"是否多个著作权人共同享有软件著作权"，并可能需要添加多个著作权人。

## 3. 字段自动推断映射（分析项目时的核心对照表）

| 申请表字段 | 能否从项目推断 | 推断来源 |
|---|---|---|
| 软件分类 | ✅ | 一般项目默认"应用软件"；嵌入式/中间件/操作系统按项目性质判断 |
| 软件全称/简称 | ⚠️ 建议权 | 项目名+功能定位给建议，用户定稿 |
| 版本号 | ✅ | git tag、package.json、发布记录 |
| 权利取得方式/权利范围 | ⚠️ 默认 | 默认原始取得+全部权利，特殊情况用户确认 |
| 开发方式 | ❌ | 用户提供；非单独开发触发权属文件提醒 |
| 开发完成日期 | ✅ | git 最后提交/发布日期 |
| 发表状态/首次发表日期地点 | ⚠️ | 有公开发布记录可推断"已发表"，地点通常用户确认 |
| 著作权人 | ❌ | 用户提供（与实名认证一致） |
| 硬件环境（开发/运行） | ✅ | 通用描述即可（≤50 字），从部署配置推断 |
| 操作系统（开发/运行） | ✅ | 项目配置、Dockerfile、CI 配置 |
| 开发环境/开发工具 | ✅ | 构建工具、IDE 配置 |
| 运行支撑环境/支持软件 | ✅ | 依赖清单：运行时、数据库、中间件 |
| 编程语言 | ✅ 精确 | 代码统计；注意 21 项复选列表外的语言（TypeScript/Kotlin/Rust 等）写入"其他编程语言"（≤120 字） |
| 源程序量 | ✅ 精确 | 代码行数统计（口径：不含空行；第三方代码不计） |
| 开发目的 | ✅ | README/项目定位归纳，≤50 字 |
| 面向领域/行业 | ✅ | 功能归纳，≤50 字 |
| 软件的主要功能 | ✅ 生成 | **500–1300 字，有下限**；从 README、菜单/路由结构、模块划分归纳 |
| 软件的技术特点 | ✅ 生成 | 15 个类别复选（APP/大数据/人工智能等）+ ≤100 字文本概括架构特点 |
| 程序/文档鉴别材料 | ✅ 生成 | 从源码/文档生成符合规范的 60 页 PDF |
| 身份证明、权属合同 | ❌ | 用户准备，agent 提醒 |

## 4. 差距分析检查清单（整改建议触发条件）

分析项目目录时逐项检查，不满足则输出整改建议：

- [ ] 源代码总量 ≥3000 行（约 60 页）？不足 → 建议补充功能模块或增加注释充实（说明交存规则：不足 60 页须全部提交）
- [ ] 代码中是否有大段空行/无意义注释？→ 提示排版要求：每页 ≥50 行、避免大段空行
- [ ] 是否有 README 或设计/使用文档？没有 → 需编写用户手册或设计说明书（文档鉴别材料）
- [ ] 文档是否有界面截图？纯文字文档通过率差 → 建议补充图文说明
- [ ] 软件名称、版本号在代码/文档/页眉中是否一致？→ 一致性是审查点
- [ ] 是否有开源许可证冲突或大量第三方代码？→ 提醒鉴别材料中避免包含第三方代码
- [ ] 开发方式若为非单独开发 → 提醒准备对应权属证明文件
- [ ] git 历史是否完整？日期推断依赖提交记录

## 5. 生成写作指导

### 5.1 软件的主要功能（500–1300 字）

- 按功能模块分条描述，覆盖系统主要功能点，忌只写概括性一段话（容易不足 500 字）
- 素材来源：README 功能列表、路由/菜单定义、控制器/服务模块划分、数据库表结构反映的业务域
- 语气：客观陈述，"本软件/系统用于……，主要功能包括：1.……"

### 5.2 软件的技术特点（≤100 字文本 + 类别勾选）

- 文本写架构与技术亮点：架构模式（前后端分离/微服务）、关键技术（缓存、消息队列、算法）、性能与安全设计
- 类别按实际勾选（可多选）：如含 AI 对话能力勾"人工智能软件"，含移动端勾"APP"或"小程序"

### 5.3 源代码 PDF 生成要点

- 选取最具独创性的核心代码（可按功能主次排序），跳过第三方库、自动生成代码、配置文件
- 去空行后每页 ≥50 行；页眉标注软件全称+版本号，页码连续
- 前后各 30 页；总量不足 3000 行时全部放入

## 6. 常见错误（整改建议高频项）

| 错误 | 后果 | 建议 |
|---|---|---|
| 主要功能描述不足 500 字 | 无法提交（表单有字数下限） | 按模块展开到 500 字以上 |
| 简称填"无" | 不符合填报说明 | 留空 |
| 材料中名称/版本号不一致 | 补正 | 全文统一 |
| 源代码含大量第三方代码 | 独创性存疑 | 只选自主代码 |
| 未发表但填了发表日期 | 逻辑矛盾 | 联动字段按发表状态填写 |
| 合作/委托开发无权属文件 | 补正或不予受理 | 先准备合同/协议再提交 |
