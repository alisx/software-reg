# 软著申请整改工具

把 `/check` 报告中的问题项或 `/plan` 输出的工作项整理成一份可执行的整改清单，自动完成其中可由 agent 代办的整改（如统一软件名称、统一版本号、补齐缺失文档骨架），其余项整理为人工待办，减少重复劳动。

目标项目目录：`$ARGUMENTS`（为空则为当前工作目录）。若当前会话已有 `/check` 或 `/plan` 的报告，直接以其为整改来源；否则先按 `commands/check.md` 第 1 节的步骤快速扫描，得出问题清单。

依据：`software-reg` skill 第 2 节硬性规范、第 4 节检查清单；优先级分级（P0/P1/P2）与 `/check` 报告保持一致。

## 执行步骤

### 1. 整理整改清单

把问题项与工作项按下表分类输出，这是本命令的核心交付物之一：

| 类别 | 含义 | 典型项 |
|---|---|---|
| A 自动可改 | agent 可直接修改文件完成 | 统一软件名称、统一版本号、删除大段连续空行 |
| B 可生成草稿 | agent 生成初稿，用户补充 | README 补全、用户手册/设计说明书骨架（含截图占位） |
| C 用户必办 | 无法代办，给出明确指引 | 界面截图、实名认证、权属合同、开发方式确认 |

每条注明：来源（check 第 N 项 / plan 工作项）、优先级（P0/P1/P2）、目标状态（改到什么程度算完成）。

### 2. 预览改动并等用户确认

**未获用户明确确认前，不修改目标项目的任何文件。** 确认前输出：

- 改动对照表：每个待修改文件 → 改动内容（如 `旧名称 → 新名称` 出现 N 处、`版本 0.9 → V1.0` 出现 M 处）
- 软件名称以用户给定的目标全称为准；用户未给定时，先按 skill 第 2.2 节命名惯例给建议值，等用户拍板
- 版本号以权威来源为准（优先级：git tag > 清单文件 version > 文档），存在冲突时列出由用户选择
- 目标项目在 git 仓库中且有未提交改动时，提醒用户先提交或备份

### 3. 执行自动整改（确认后）

- **名称统一**：对源代码注释头部、README、文档、清单文件 description 等文本文件做精确字符串替换；逐文件记录替换处数；完成后用 Grep 复核残留旧名称并列出
- **版本统一**：同步各清单文件与文档中的版本号；保持 `V数字`/`数字` 格式（skill 第 2.2 节）
- **空行清理**：仅对用户明确选择的文件，把 3 行以上连续空行压缩为 1 行；默认不执行
- **文档骨架**：生成缺失的 README 章节或用户手册/设计说明书骨架，截图位置留占位标记（如 `【此处插入 XX 界面截图】`），并在报告中列出待补截图清单

不触碰：`node_modules`、`vendor`、`.venv`、`dist`、`build`、`target`、`.git` 等第三方与生成物目录；不删除任何文件；不做模糊批量替换（仅精确匹配）。

### 4. 输出整改报告

```markdown
# 软著申请整改报告：<项目名>

## 整改清单总览
| 类别 | 事项 | 优先级 | 状态 |
（状态：✅ 已自动完成 / 📄 已生成草稿 / ⏳ 待用户办理）

## 已自动完成的修改
| 文件 | 改动 | 处数 |
（含名称/版本替换后的 Grep 复核结果）

## 已生成的草稿
<新建/补全的文档清单 + 待补截图清单>

## 仍需用户办理
| 事项 | 具体指引 | 阻塞关系 |
（每条写清做什么、做到什么程度、是否阻塞提交申请）

## 遗留风险
<整改后仍存在的差距，如代码量仍不足 3000 行>
```

## 边界

- 确认前只输出不改文件；确认是执行修改的硬性前提
- 只修改文本文件，不删文件，不动第三方与生成物目录
- 修改后须复核（Grep 残留检查）并在报告中如实列出未能处理的项
- C 类（用户必办）事项不代办、不臆造（如不编造开发方式、不生成虚假截图）
- 目标目录不存在或不是代码项目时，直接说明并停止
