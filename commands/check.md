# 软著申请差距分析

分析目标项目是否满足软著（计算机软件著作权）登记申请的材料要求，输出差距报告和整改建议。

目标项目目录：`$ARGUMENTS`（为空则为当前工作目录）

判定依据：`software-reg` skill 中的硬性规范（第 2 节）和检查清单（第 4 节）。官方要求原文见 skill 的 references/ 下三页字段文档，引用说明文字时不得改写。

## 执行步骤

### 1. 扫描项目

用 Bash / Glob / Grep 收集以下事实，全部以实际扫描结果为准，不得臆测：

- **代码量**：按编程语言统计代码行数（排除空行）。必须排除第三方与生成物目录（`node_modules`、`vendor`、`.venv`、`venv`、`dist`、`build`、`target`、`.git` 等），并说明统计口径
- **语言分布**：各语言文件数与行数占比
- **文档**：是否存在 README / 用户手册 / 设计说明书 / 使用文档；文档中是否有界面截图（图片引用）
- **版本信息**：`package.json`、`pyproject.toml`、`Cargo.toml`、`pom.xml` 等清单文件中的 name/version；git tag
- **git 历史**：首次提交与最后提交日期（用于推断开发完成日期）；无 git 仓库时明确标注
- **第三方代码**：依赖规模、是否有 LICENSE / 开源许可证、是否存在大段复制粘贴的第三方源码
- **命名一致性**：项目名在不同文件（清单、README、文档）中的写法是否一致

### 2. 逐项判定

对照下表判定（完整清单与官方原文见 skill）：

| # | 检查项 | ❌ 不满足的判定条件 |
|---|---|---|
| 1 | 源代码量 | 自主代码（去空行）< 3000 行（约 60 页 × 50 行） |
| 2 | 代码排版 | 存在大段连续空行或无意义填充注释 |
| 3 | 文档材料 | 无任何 README / 手册 / 设计文档 |
| 4 | 文档质量 | 有文档但纯文字、无界面截图 |
| 5 | 命名一致性 | 名称或版本号在多处文件中不一致 |
| 6 | 第三方代码 | 鉴别材料可能混入第三方/自动生成代码 |
| 7 | git 历史 | 无 git 历史，开发完成日期无法推断 |
| 8 | 许可证 | 存在传染性开源协议或权属不明的代码 |

### 3. 输出报告

```markdown
# 软著申请差距分析报告：<项目名>

## 总体结论
<一段话：当前是否具备直接申请的条件，最大的短板是什么>

## 关键数据
<代码量、语言分布、文档情况、日期范围——只列扫描到的事实>

## 检查结果
| # | 检查项 | 状态 | 发现 | 整改建议 |

状态：✅ 满足 / ⚠️ 需注意 / ❌ 不满足。每条整改建议必须可执行（做什么、做到什么程度）。

## 整改行动项
按 P0（不解决无法申请）/ P1（影响通过率）/ P2（可选优化）分级列出。
```

## 边界

- 只做分析与建议，不修改目标项目的任何文件
- 开发方式、著作权人等无法从代码推断的信息，不臆测；在报告中列入"需用户确认"一节
- 目标目录不存在或不是代码项目时，直接说明并停止
