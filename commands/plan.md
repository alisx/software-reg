# 软著申请材料准备规划

为目标项目制定一份软著（计算机软件著作权）登记申请的材料准备计划：要准备哪些材料、哪些 agent 可以代办、哪些必须由用户完成、按什么顺序准备。

目标项目目录：`$ARGUMENTS`（为空则为当前工作目录）

依据：`software-reg` skill 第 1 节（申请流程）、第 2 节（硬性规范）、references/ 下三页字段文档。

## 执行步骤

### 1. 快速摸底（只读）

轻量扫描目标项目，确定规划依赖的事实（不需要像 `/check` 那样全面）：

- 代码量是否 ≥3000 行（决定源程序鉴别材料是"前后各 30 页"还是"提交全部"）
- 是否已有可用文档（README / 用户手册 / 设计说明书）、是否有界面截图
- 是否有 git 历史（日期推断依据）
- 是否有公开发布记录（影响发表状态相关字段）

如用户已提供开发方式、著作权人等背景信息，纳入规划；未提供则按"待确认"处理，不臆测。

### 2. 输出准备计划

```markdown
# 软著申请材料准备计划：<项目名>

## 材料清单
| 材料 | 规范要求 | 谁来准备 | 当前状态 | 说明 |

规范要求引用 skill 第 2 节硬性规范（官方原文不得改写）。"谁来准备"只分两类：
- **agent 可代办**：填报草稿（/fill）、主要功能与技术特点（/describe）、源代码 PDF、文档鉴别材料草稿
- **用户必办**：实名认证（流程第 1 步）、身份证明文件、权属合同（非单独开发时）、界面截图、最终确认签章（流程第 5 步）

## 准备顺序
按依赖关系排序的编号步骤，例如：先定稿软件全称/版本号（所有材料一致性前提）→ 再生成鉴别材料 → 最后填报上传。

## 预计工作量
每项材料给出粗略工作量估计（如"源代码 PDF：agent 生成约 X 分钟，用户核对"），并标出关键路径（最耗时的用户必办项）。

## 风险提示
<从摸底发现的影响申请的风险：代码量不足、文档缺失、权属文件未备等>
```

## 边界

- 只做规划，不修改目标项目的任何文件，也不实际生成材料（生成由 /fill、/describe 等命令执行）
- 开发方式、著作权人等背景信息未提供时按"待确认"列出，不臆测
- 鉴别材料 PDF 的实际排版生成（每页 ≥50 行、页眉页码）如超出当前能力，如实说明并给出替代操作建议
- 目标目录不存在或不是代码项目时，直接说明并停止
